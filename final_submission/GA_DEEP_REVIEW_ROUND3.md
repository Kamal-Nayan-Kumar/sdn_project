# HIGH LEVEL SUMMARY
---
## Summary
This paper presents a bounded agentic automation framework for intent-based self-healing in Software-Defined Networks (SDNs) built on a 13-node LangGraph state machine. To prevent probabilistic Large Language Model (LLM) hallucinations or naive automated reroutes from degrading live networks, the authors confine the LLM strictly to natural-language intent parsing and post-hoc diagnostic narration while delegating path computation and execution gating to a deterministic graph planner and three deterministic Python gates: an evidence sufficiency gate (Gate 1), a nine-check static safety validator (Gate 2), and a post-execution outcome verification gate (Gate 3). Evaluated across eight scenarios on a four-switch Mininet/Ryu OpenFlow 1.3 testbed—both with a deterministic keyword-parser fallback and with an active LLM—the system demonstrates verified congestion recovery, shared sample-distribution latency validation, and explicit, auditable refusal and abstention outcomes.

## Strengths
* The paper addresses a critical operational challenge in network automation—bridging the gap between command execution success and measured data-plane outcome success—by elevating explicit, auditable refusals and abstentions (`no_better_path`, `partial_improvement`, `abstained_insufficient_evidence`, `lab_offline`) to first-class terminal outcomes.
* Using a shared sample-distribution latency predicate ($\ge 25\%$ of samples exceeding target $\tau$) across both pre-action violation detection (Gate 1) and post-action verification (Gate 3), combined with a strict delay-improvement pre-filter, prevents verdict drift between gates, tolerates single-sample host-scheduling spikes, and prevents "always-act" regressions on healthy networks.
* The authors demonstrate commendable scientific transparency and engineering rigor by shipping a reproducible artifact, reporting multi-trial outcome distributions, and documenting a candid "truth audit" of prior hardware/software limitations and open trust boundaries.

## Weaknesses
* The core architectural components represent an incremental engineering synthesis of established paradigms, and the claim that prior agentic systems do not gate actions on post-change measured outcome verdicts via a deterministic state machine overlooks recent autonomous remediation and closed-loop SDN frameworks that already formalize state-machine-enforced post-mutation verification, non-regression gating, and LLM-assisted Ryu assurance (Reference Paper: STRATUS: A Multi-agent System for Autonomous Reliability Engineering of Modern Clouds, Yinfang Chen et al., 2025; Reference Paper: NetIntent: Leveraging Large Language Models for End-to-End Intent-Based SDN Automation, Md. Kamrul Hossain and Walid Aljoby, 2025; Reference Paper: Hey, Lumi! Using Natural Language for Intent-Based Network Management, Arthur S. Jacobs et al., 2021; Reference Paper: ONOS Intent Monitor and Reroute Service: Enabling Plug & Play Routing Logic, Davide Sanvito et al., 2018; Reference Paper: VeriFlow: Verifying Network-Wide Invariants in Real Time, Ahmed Khurshid et al., 2013; Reference Paper: Pingmesh: A Large-Scale System for Data Center Network Latency Measurement and Analysis, Chuanxiong Guo et al., 2015).
* When link utilization is below $80\%$, Gate 1's path-delay fallback places *all* inter-switch links along the current path into the suspect set $C_{\text{susp}}$, and Equation (5) strictly disqualifies any candidate path sharing even a single edge with $C_{\text{susp}}$; consequently, the planner is mathematically incapable of finding a valid recovery path in any realistic network topology where the source or destination switch connects to the core via a single healthy aggregation uplink (a cut-edge/bridge).
* In Scenario S8 (unflagged delay degradation), the system does not actually infer per-link delay from live data-plane probes, as Gate 1 and the planner rely directly on a lab-supplied effective delay value ($d_e^{\text{eff}}$) in the snapshot $\Sigma$; meanwhile, Gate 2's capacity check (`Check 6`) ignores $C_{\text{susp}}$ and $d_e^{\text{eff}}$ and passes vacuously whenever the oracle flag $C_{\text{deg}}$ is absent and utilization is below $80\%$, meaning Gate 2 cannot independently block an unflagged delay bottleneck if the upstream planner fails to exclude it.
* The empirical evaluation is restricted to internal single-rule ablations on a single flow across a 4-switch userspace Python switch testbed ($\sim 56\text{ Mbit/s}$ ceiling, where the offered-load scenario S7 retains synthetic `netem` delay to breach the $50\text{ ms}$ target and the protected voice flow has an empty inter-switch edge set $E_{\text{prot}} = \varnothing$), and the LLM is tested on only a single happy-path prompt per scenario rather than evaluated against external closed-loop SDN baselines or established multi-topology troubleshooting and intent benchmarks (Reference Paper: NIKA: A Network Arena for Benchmarking AI Agents on Network Troubleshooting, Zhi-Hao Wang et al., 2025; Reference Paper: Benchmarking LLM-Driven Network Configuration Repair, Ioannis Protogeros et al., 2026; Reference Paper: NetIntent: Leveraging Large Language Models for End-to-End Intent-Based SDN Automation, Md. Kamrul Hossain and Walid Aljoby, 2025; Reference Paper: Intent-Driven Network Management with Multi-Agent LLMs: The Confucius Framework, Zhaodong Wang et al., 2025).
* Several mathematical and procedural discrepancies exist across the manuscript—including the omission of the strict delay-improvement pre-filter from Section V, asymmetry in packet-loss handling between Gate 1 and Gate 3, lack of automatic rollback when Gate 3 detects a post-mutation regression (`recovery_failed`), and missing wall-clock columns in Tables IV and VIII—which the authors might consider resolving to strengthen the specification.

#### Potential Mistakes and Improvements

1. **Positioning Against Prior Closed-Loop and Verifier-Gated Agentic Systems (Section II-C and Section II-D)**
   - **Potential Concern:** In Section II-C (page 2, right column), the text characterizes closest prior art—including ONOS's Intent Monitor and Reroute (IMR) service [11], Lumi [12], NetConfEval [13], Confucius [14], and Protogeros et al. [15]—by stating: *"These systems are all either implicitly closed-loop (ONOS: monitor and reroute) or model-centred with external checkers (Lumi, NetConfEval, Confucius, Protogeros): in each of them the decision to change the network is taken inside a model-centred loop, or correctness is judged at configuration time. None gates the action on a post-change measured outcome verdict, and none makes refusal an explicit, audited, first-class outcome."* While this distinction accurately contrasts the proposed deterministic three-gate architecture against configuration-time synthesis verifiers and model-orchestrated workflows, there are two areas where this positioning could be refined for precision and completeness:
     1. *Characterization of ONOS IMR [11] and Lumi [12]:* Neither ONOS IMR [11] nor Lumi [12] operates an autonomous LLM-centred loop. Lumi translates natural-language intents into the structured Nile intermediate representation using sequence-to-sequence entity extraction and requires explicit operator confirmation prior to compilation and deployment, whereas ONOS IMR is a deterministic control-plane monitoring and rerouting loop. Grouping them under the summary statement *"in each of them the decision to change the network is taken inside a model-centred loop, or correctness is judged at configuration time"* risks conflating classical closed-loop SDN intent rerouting and pre-LLM intent compilation with LLM-in-the-loop configuration synthesis. Explicitly separating deterministic control-plane rerouting without a post-mutation SLA verification/refusal taxonomy (ONOS IMR) from pre-deployment configuration verifiers and model-centred tool orchestration (Lumi, VPP [17], NetConfEval, Confucius, Protogeros et al.) would make the taxonomy in Section II-C more accurate.
     2. *Scope of Empirical Baseline Comparisons:* Sections II-C and II-D establish ONOS IMR [11] and verifier-in-the-loop LLM repair [15], [17] as the primary conceptual alternatives to the proposed deterministic-planner/three-gate architecture. However, the empirical evaluation in Sections VIII–IX tests only internal single-component ablations (shortest-path ranking, mean-only violation predicate, and an always-act policy) rather than benchmarking against an external closed-loop rerouting service or a verifier-in-the-loop LLM path-proposal baseline. While Sections I and XI transparently acknowledge that multi-topology and adversarial-model evaluations are left to future work, explicitly clarifying in Section I or Section II that the empirical comparisons are designed to isolate internal architectural components via ablations rather than benchmark against external agent loops would align the related-work framing with the evaluation setup.

### [System Model, Mathematical Formulation & Guarded Recovery Algorithm] (Pages: 3-8, 15)
#### Potential Mistakes and Improvements

1. **Topological Brittleness and Unused Ordering of $C_{\text{susp}}$ in Gate 1's Path-Delay Fallback (`Section V-B`, Eqs. 5–6; `Section VI-B`; `Section X`; `Section XI`, Roadmap Item 6; `Algorithm 1`, Line 17)**
   - **Reference:** Section V-B (Eqs. 5–6, page 5), Section VI-B (page 7), Section X (page 13), Section XI (Roadmap Item 6, page 14), and Algorithm 1 (line 17, page 15).
   - **Potential Concern:** In Section VI-B (page 7) and Algorithm 1 (line 17, page 15), when no link exceeds the $80\%$ utilization threshold ($u_e \ge 80\%$), the path-delay fallback populates the suspect set $C_{\text{susp}}$ with *all* switch edges along the flow's current path $p_{\text{curr}}$ (*"if no link is congested, the path-delay fallback names all links on the flow's current path, sorted by effective delay descending with link-id tie-breaking"*). Simultaneously, the candidate-filtering predicate in Eq. (5) requires a candidate path $p$ to be strictly edge-disjoint from $C_{\text{deg}} \cup C_{\text{susp}}$ ($A(p) = [E_p \cap (C_{\text{deg}} \cup C_{\text{susp}}) = \varnothing]$), and Eq. (6) assigns $\text{score}(p) = +\infty$ whenever $\neg A(p)$ (while Algorithm 1, line 17 excludes suspect-crossing paths from $\mathcal{P}_c$). While Section VI-B transparently acknowledges that placing the healthy upstream link `s1-s2` in $C_{\text{susp}}$ disqualifies the valid bypass path `s1-s2-s3-s4` in the four-switch ring topology, this design introduces two broader structural concerns (and is not addressed in Section X *Limitations* or Section XI *Roadmap Item 6* when proposing to port the evaluation to larger topologies such as the Internet Topology Zoo):
     1. *Candidate path starvation on non-ring and WAN/ISP topologies:* Under any pure-delay fault where $u_e < 80\%$ (as in S2, S3, and S8), placing all switch edges of $p_{\text{curr}}$ into $C_{\text{susp}}$ mandates that a valid repair path be completely switch-edge-disjoint from $p_{\text{curr}}$ ($E_p \cap E_{p_{\text{curr}}} = \varnothing$). While the 4-switch ring-with-diagonal lab topology has a completely switch-edge-disjoint backup path (`s1-s3-s4` vs. `s1-s2-s4`), realistic WAN/ISP topologies in the Internet Topology Zoo frequently contain stub attachments, degree-2 access aggregation, or shared core/egress trunks (a cut-edge/bridge in $E_S$) where no fully edge-disjoint end-to-end path exists between two access switches, or where all feasible detour paths share at least one healthy transit link with $p_{\text{curr}}$. In such topologies, $A(p)$ evaluates to false for *every* candidate path, preventing recovery even when alternative core sub-paths around the degraded link exist.
     2. *Mathematically unused sorting of $C_{\text{susp}}$:* Section VI-B and Algorithm 1 (line 17) specify that $C_{\text{susp}}$ is sorted by effective delay descending with link-id tie-breaking. However, Eq. (5) consumes $C_{\text{susp}}$ strictly as an unordered set in an unweighted intersection test, so the sorting step has no mathematical effect on candidate filtering or scoring in Eqs. (5)–(6).
   - **Suggested Improvement:** Since both per-link effective delay $d_e^{\text{eff}}$ and configured baseline delay $d_e$ are available in the observation snapshot $\Sigma$ (Section IV-B), the authors could restrict $C_{\text{susp}}$ in the path-delay fallback to links whose effective delay exceeds their configured baseline ($d_e^{\text{eff}} > d_e$) or to a top-$k$ (e.g., $k=1$) prefix of the sorted suspect list, or alternatively replace hard set disjointness in Eq. (5) with a soft penalty in Eq. (6) when no strictly edge-disjoint path exists. Explicitly acknowledging this full-path disjointness constraint in Section X and noting in Roadmap Item 4 or 6 that scaling to general topologies requires refining how $C_{\text{susp}}$ is populated (e.g., via excess effective delay $d_e^{\text{eff}} > d_e$ or intersecting probe paths) would also strengthen the scaling roadmap.

2. **Discrepancies Between Section V and Algorithm 1 Regarding the Improvement Pre-Filter (`not_an_improvement`), Upstream Candidate Exclusion, Check 6 Reachability, and Unassigned `lab_offline` (`Section V-B`, `Section V-C`, `Section VI-A`, `Section VI-C`, `Section X`, `Section XI`, and `Algorithm 1`, Lines 8–24)**
   - **Reference:** Section V-B (Eqs. 5–6, page 5), Section V-C (page 5), Section VI-A (page 6), Section VI-C (page 7), Section X (page 13), Section XI (page 14), and Algorithm 1 (lines 8–24, page 15).
   - **Potential Concern:** Cross-checking the mathematical definitions in Sections V-B and V-C and the prose in Sections VI, X, and XI against the procedural workflow in Algorithm 1 reveals four specification gaps that represent a potential concern for independent reimplementation and outcome reachability:
     1. *Omission of the strict delay-improvement pre-filter from Section V and interaction with organic congestion:* In Algorithm 1 (lines 18–21), the `validate` node begins by pre-filtering $\mathcal{P}_c$ using a strict delay-improvement test: any candidate whose effective switch delay $D(p)$ is not strictly less than the current path's effective delay $D(p_{\text{curr}})$ is dropped before any of the nine safety checks of Section V-C are evaluated, recording `failed_checks = [not_an_improvement]` and terminating with `no_better_path` (line 20) if no candidate survives. Although this check is the sole mechanism that produces the `no_better_path` refusal in Scenario S4 (preventing the agent from installing the 12 ms path `s1-s3-s4` over the healthy 8 ms path `s1-s2-s4`), the predicate $D(p) < D(p_{\text{curr}})$ is omitted from the mathematical formulation in Sections V-B and V-C (and the prose of Section VI-C). Based on Section V alone, `s1-s3-s4` in Scenario S4 satisfies $A(p)$, receives a finite score in Eq. (6), and passes all nine checks in Section V-C. Conversely, under Roadmap Item 3 (page 14)—where organic queueing delay is induced by offered load *without* synthetic `netem` link-delay injection—if $d_e^{\text{eff}}$ remains the static configured link delay unless dynamically measured (Roadmap Item 4), a congested shortest path (`s1-s2-s4`, nominal $D(p) = 8\text{ ms}$, $u_e \ge 80\%$) would have a smaller nominal $D(p)$ than an uncongested backup path (`s1-s3-s4`, $D(p) = 12\text{ ms}$), causing line 18 to drop `s1-s3-s4` via `not_an_improvement`.
     2. *Upstream exclusion vs. $+\infty$ scoring and broader vacuity of Gate 2's Check 6:* In Section V-B, Eq. (6) assigns $\text{score}(p) = +\infty$ to paths failing $A(p)$, implying they remain in $\mathcal{P}_c$ with an infinite score. By contrast, Section V-C (page 5), Section VI-C (page 7), Section X (page 13, second bullet), and Algorithm 1 (line 17: $\mathcal{P}_c \leftarrow \text{candidate paths avoiding suspects, ranked by Eq. (6)}$) state that candidates failing $A(p)$ are excluded from $\mathcal{P}_c$ upstream before Gate 2 (`validate`) is consulted. If the planner removes all paths violating $A(p)$ at line 17, then Gate 2's Check 6 (`capacity_respected`: $e \notin C_{\text{deg}}$ and $u_e < 80\%$) does not merely pass vacuously in the unflagged delay scenario (S8)—it passes vacuously for *every* candidate reaching line 22 across *all* scenarios (including S2, S3, and S7), because $A(p)$ already excludes $C_{\text{deg}}$ and rule (i) of Gate 1 already places every link with $u_e \ge 80\%$ into $C_{\text{susp}}$.
     3. *Ambiguity when $\mathcal{P}_c = \varnothing$ entering `validate`:* If `diagnose` (line 17) hard-filters paths intersecting $C_{\text{deg}} \cup C_{\text{susp}}$ out of $\mathcal{P}_c$ without recording a rejection reason and yields an empty candidate set $\mathcal{P}_c = \varnothing$, then at line 18 zero candidates are dropped during the pre-filter. At line 19 (*"if no candidate survives the pre-filter and every recorded rejection is a non-improvement"*), it is ambiguous whether universal quantification over an empty set of recorded rejections holds vacuously (routing a suspect-starved network to `no_better_path` at line 20) or requires at least one `not_an_improvement` rejection (falling through to line 23 and routing to `action_rejected` at line 24).
     4. *Unreachable `lab_offline` in Algorithm 1 pseudocode:* While the `Ensure:` specification of Algorithm 1 (page 15) lists `lab_offline` as a terminal outcome—and claims in the caption that *"the routing is the routing function of the implementation, not a paraphrase of it"*—no line in the body of Algorithm 1 ever assigns `o <- lab_offline`. Line 8 states `observe: \Sigma_0 <- \Sigma(I) // fails if the lab is unreachable`, and when `observe` fails, control flows to the `else` branch at lines 14–15, which unconditionally assigns `o <- abstained_insufficient_evidence via abstain; return`.
   - **Suggested Improvement:** Explicitly incorporate the strict improvement predicate $D(p) < D(p_{\text{curr}})$ into Section V-B/V-C (and note in Section X / Roadmap Items 3–4 that the line 18 improvement filter must account for congestion or measured RTT under organic queueing), clarify whether paths failing $A(p)$ are hard-filtered at line 17 or passed with score $+\infty$ to `validate`, specify the exact branching condition at lines 18–24 of Algorithm 1 when $\mathcal{P}_c$ is empty prior to pre-filtering, and explicitly reflect the `lab_offline` state preservation (described in Section VI-A) at lines 8 and 15 of Algorithm 1.

3. **Asymmetry in Packet-Loss Handling Between Pre-Action Violation Detection (Gate 1) and Post-Action Verification (Gate 3) (`Section IV-A`, Eq. 3; `Section V-A`, Eq. 4; `Section V-D`, Eq. 7; `Algorithm 1`, Lines 9–11)**
   - **Reference:** Section IV-A (Eq. 3, page 4), Section V-A (Eq. 4, page 4), Section V-D (Eq. 7, page 6), and Algorithm 1 (lines 9–11, page 15).
   - **Potential Concern:** Eq. (3) defines the controlled intent tuple as $I = (s, t, \tau, \ell, \mathcal{P})$, where $\ell$ is an optional packet-loss target, and Section IV-B states that per-flow measurements include loss $p_f$. In Section V-A, packet loss $p_f$ is deliberately omitted from the violation predicate $v(f, I)$ in Eq. (4) so that $v(f, I)$ evaluates only the latency distribution, while $\ell$ is evaluated post-action via $L \equiv (\ell \text{ undeclared}) \lor (p_{f^+} \le \ell)$ in Gate 3's verification verdict $\mathcal{V}$ (Eq. 7) to keep row 3 of Eq. (7) (`partial`, when $\neg v(f^+, I) \land \neg L \land Q$) reachable. However, using $v(f, I)$ alone as the Gate 1 satisfaction check in Algorithm 1 (line 10: `if` $v = \text{false} \land e = \text{sufficient}$ `then` $o \leftarrow \text{intent\_satisfied}$) creates two logical discrepancies whenever $\ell$ is declared:
     1. *Unremediated pre-action packet loss:* If a flow experiences severe packet loss ($p_{f^-} > \ell$) while its surviving ping samples remain below the latency target $\tau$ ($v(f^-, I) = \text{false}$), Gate 1 immediately returns `intent_satisfied` without entering `diagnose` or attempting recovery.
     2. *Gate 1 vs. Gate 3 disagreement on identical network state:* If a flow has high latency, is rerouted onto a path that satisfies $\tau$ ($\neg v(f^+, I)$) but suffers packet loss ($p_{f^+} > \ell$, so $\neg L$), Gate 3 (Eq. 7, row 3) returns `partial_improvement`. Yet if the agent is immediately re-run on that exact post-action network state, Gate 1 evaluates $v(f, I) = \text{false}$ (ignoring $L$) and declares `intent_satisfied`—the exact kind of inter-gate disagreement on the same measurement that Section V-D notes the shared predicate is meant to prevent.
   - **Suggested Improvement:** Keep $v(f, I)$ in Eq. (4) as a pure latency-distribution predicate (preserving the disjoint scope and reachability of row 3 in Eq. 7), and either update Gate 1's satisfaction condition at line 10 of Algorithm 1 (and Section VI-B) to require $\neg v(f^-, I) \land L(f^-) \land (e = \text{sufficient})$, or state explicitly in Section V-A that remediation in the evaluated prototype is strictly latency-triggered and $\ell$ serves solely as a post-action verification guard.

4. **Lack of an Independent Safety Backstop in Gate 2 (`capacity_respected`, Check 6) for Unflagged Delay Faults (`Section IV-C`, `Section V-C`, and `Section VI-C`)**
   - **Reference:** Section IV-C (page 4), Section V-C (Check 6, page 5), and Section VI-C (page 7).
   - **Potential Concern:** Section IV-C establishes the core architectural principle that the planner is untrusted and Gate 2 serves as the sole deterministic trust boundary protecting the data plane (*"The only edge from $D$ into the data plane passes through the safety gate"*). However, Check 6 (`capacity_respected`) only verifies $e \notin C_{\text{deg}}$ and $u_e < 80\%$; it neither checks $e \notin C_{\text{susp}}$ nor enforces a bound on effective delay $d_e^{\text{eff}}$. As the authors transparently document in Sections V-C and VI-C, under an unflagged latency fault ($C_{\text{deg}} = \varnothing$ and $u_e \approx 0\%$, as in Scenario S8), Check 6 passes vacuously for every candidate path—including the degraded bottleneck `s2-s4`—leaving safety entirely dependent on the upstream planner's candidate exclusion in Eq. (5). If the planner were replaced by an untrusted model or contained a bug, Gate 2 would admit a reroute straight across the fault.
   - **Suggested Improvement:** Even though empirical evaluation of a decoupled check is noted as future work, specifying the exact formal predicate required to close this boundary within the existing observation model $\Sigma$ in Section V-C (such as requiring $e \notin C_{\text{susp}}$, $d_e^{\text{eff}} \le \alpha d_e$, or incorporating $D(p) < D(p_{\text{curr}})$ directly as a numbered safety check in Gate 2) would align the mathematical formulation of Gate 2 with its stated role as an independent trust boundary.

5. **Incomplete Formal Specification of Evidence Sufficiency ($e$), Protected-Flow Constraints ($\mathcal{P}, \mathcal{Q}$), and Effective-Delay Telemetry ($d_e^{\text{eff}}$) (`Section IV-A–B`, `Section V-A`, `Section V-D`, and `Section VI-B`)**
   - **Reference:** Section IV-A–B (page 4), Section V-A (page 4), Section V-D (page 6), Section VI-B (page 7), and Algorithm 1 (line 9, page 15).
   - **Potential Concern:** While Gate 2 and Gate 3 are defined with exact mathematical equations in Section V, three components needed for an independent reimplementation are described only qualitatively in prose:
     1. *Evidence sufficiency predicate $e$:* Algorithm 1 (line 9) computes `(e, freshness) <- the evidence verdict` and branches on `e = sufficient`, and Section VI-B states that Gate 1 checks whether measurements *"exist, are recent enough under the configured policy (five seconds), are numerically sane, and support a diagnosis."* However, Section V-A does not provide a formal definition of $e(\Sigma, I)$ specifying the exact numerical sanity criteria (e.g., minimum sample count $n$, valid bounds on $s_i$, $u_e$, $p_f$) and diagnostic prerequisites.
     2. *Protected-flow tuple $\mathcal{P}$ and evaluation $\mathcal{Q}$:* Eq. (3) includes the set of protected flows $\mathcal{P}$, and Section V-D defines $\text{ok}(q)$ for $q \in \mathcal{Q}$ as holding when a protected flow's *"measured latency is within its own constraint, its loss (if constrained) is within its own limit, and its path is unchanged from before the action."* Neither the formal tuple structure of an element in $\mathcal{P}$ (e.g., $(s_q, t_q, \tau_q, \ell_q, p_q)$) nor the numerical latency/loss thresholds configured for the protected voice flow `h3->h4` are stated in Sections IV–VII.
     3. *Telemetry source of $d_e^{\text{eff}}$ in $\Sigma$ and delay arithmetic in Section VI-B:* Section IV-B defines per-link telemetry as $\ell_e = (u_e, c_e, d_e^{\text{eff}}, \text{status}_e)$ and states that *"Every element of $\Sigma$ is measured: latency by ICMP echo executed inside the hosts, utilisation by the datapath's own port counters, and link status by the controller."* Because standard OpenFlow 1.3 switches do not natively measure per-link one-way delay without timestamping probes, Section IV-B should state explicitly that $d_e^{\text{eff}}$ is a per-link state value reported directly by the lab API (configured delay plus any active `netem` delay) rather than inferred by decomposing host ICMP probes. Additionally, Section VI-B (page 7, right column) states: *"s2-s4 carries the injected 40 ms of effective delay (48 ms total) and s1-s2 carries its configured 4 ms"*. Because $d_{\text{s2-s4}} = 4\text{ ms}$ and $d_{\text{s1-s2}} = 4\text{ ms}$, clarifying that $d_{\text{s2-s4}}^{\text{eff}} = 44\text{ ms}$ ($4\text{ ms} + 40\text{ ms}$) and that $48\text{ ms}$ is the total one-way path delay $D(\text{s1-s2-s4}) = 4 + 44 = 48\text{ ms}$ (and how this relates to Section VII-B's statement that `netem` injects 40 ms on *both* interfaces of `s2-s4`) will make the delay arithmetic unambiguous.

1. **Distinction Between Post-Mutation Verification Reporting and Automatic Rollback on Regression (Section X; Section XI, Roadmap Item 6; and Algorithm 1, Lines 28–32)**
   - **Potential Concern:** The paper emphasizes that *"a successful command is never a successful recovery"* and places Gate 3 (`verify`) after `execute` to catch cases where a statically valid rule fails to meet the intent or harms a protected flow.
